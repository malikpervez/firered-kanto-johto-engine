## Actual map selection, layout formats and IDs

The target choice is substantive campaign selection. Actual `firered` uses `FIRERED`, `MAP_VERSION=firered`, `IS_FRLG=1`, `IS_HNS=0`; `hns` uses `POKEMON_HNS`, `MAP_VERSION=hns`, `IS_FRLG=0`, `IS_HNS=1`. Both use the recorded modern ARM 14.2.1 toolchain, `MODERN=1`, `TESTING=0`, `DEBUG=0`, `RELEASE=0`, `LTO=0`, `-O2`. Selector source: [Makefile](https://github.com/PokemonHnS-Development/pokehns-expansion/blob/167aa6d537b109bb229c231ddce4616974c4da71/Makefile#L7), [target macros](https://github.com/PokemonHnS-Development/pokehns-expansion/blob/167aa6d537b109bb229c231ddce4616974c4da71/include/constants/global.h#L65).

The pristine source contains 1,499 `map.json` files: 518 Emerald, 560 HnS and 421 FRLG. Four explicitly unused FRLG house maps are absent from selected groups: `Route19_UnusedHouse_Frlg`, `Route23_UnusedHouse`, `Route6_UnusedHouse_Frlg`, `SevenIsland_UnusedHouse`. This is an existing selection difference, not a local content deletion or proof that an intended quest is absent.

The generator filters **game version**, not the JSON `region`. `firered` normalizes to `frlg`. Global group/map ordering is retained while excluded entries become null; map constants can therefore exist for maps that have no selected header. Layout constants similarly retain shared ordering. A successful reference to a defined map ID is insufficient evidence that the destination exists in the target. See [map group selection, lines 705–752](https://github.com/PokemonHnS-Development/pokehns-expansion/blob/167aa6d537b109bb229c231ddce4616974c4da71/tools/mapjson/mapjson.cpp#L705), [header inclusion, 528–547](https://github.com/PokemonHnS-Development/pokehns-expansion/blob/167aa6d537b109bb229c231ddce4616974c4da71/tools/mapjson/mapjson.cpp#L528), [constants, 605–663](https://github.com/PokemonHnS-Development/pokehns-expansion/blob/167aa6d537b109bb229c231ddce4616974c4da71/tools/mapjson/mapjson.cpp#L605), [layout filtering, 754–872](https://github.com/PokemonHnS-Development/pokehns-expansion/blob/167aa6d537b109bb229c231ddce4616974c4da71/tools/mapjson/mapjson.cpp#L754), [generation rules](https://github.com/PokemonHnS-Development/pokehns-expansion/blob/167aa6d537b109bb229c231ddce4616974c4da71/map_data_rules.mk#L28).

## Scripts, callbacks, locks and state ownership

The actual assembler content boundary is [repair-010 `data/event_scripts.s`]([LOCAL_WORKSPACE]/_local/worktrees/repair-10-firered/data/event_scripts.s:605): `.if IS_FRLG` selects the FireRed include block; `.if IS_HNS` selects the HnS block at line 1865. Lexically counting every `.include` in the unprocessed file would incorrectly count inactive campaign scripts.

Read-only ELF inspection found **247 script-command slots in each target** and **682 FireRed / 694 HnS special-table slots**, measured from table-boundary addresses. Equal command-table length does not prove every opcode's behavior matches; differing special ordinals are not a stable interchange interface. Registrations, macros and generated script references must remain coordinated. See [command table](https://github.com/PokemonHnS-Development/pokehns-expansion/blob/167aa6d537b109bb229c231ddce4616974c4da71/data/script_cmd_table.inc), [actual target guards in specials]([LOCAL_WORKSPACE]/_local/worktrees/repair-10-firered/data/specials.inc:672), and private symbol evidence.

Those offsets do not establish an approved combined layout or regional ordering. Each existing target exposes one active rival name; FireRed reads SaveBlock1, HnS reads SaveBlock2. The combined product needs independent original Kanto and Johto rival records, not assignment to whichever field its current macro selects. [Placeholder selection](https://github.com/PokemonHnS-Development/pokehns-expansion/blob/167aa6d537b109bb229c231ddce4616974c4da71/src/string_util.c#L483).

Trainer teams and rematch tables are also selected, not one interchangeable global registry. The HnS branch includes Johto/later-Kanto rematches; the non-HnS branch retains a Hoenn rematch table. This requires FireRed rematch preservation work rather than silently importing the other branch. Trainer/encounter numeric IDs need logical campaign ownership and build mappings just as maps do. Exact trainer-team, item-price, encounter-slot and reward parity across the entire campaign was not enumerated.
